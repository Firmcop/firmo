Backend implementation plan

How to build the FirmPlant platform backend: architecture, modules, data model, engines, APIs, security and a phased delivery schedule. It covers the MVP and leaves room for FactoryOS, IoT and the WhatsApp engine later.

01Principles

  • The database is the source of truth; AI is not. Every figure shown publicly comes from a row that has a source, a date and a version.
  • Nothing publishes itself. Opportunities, supplier status and content only go live through an explicit approval step, which is written to the audit log.
  • Engines are pure and tested. Financial, landed-cost and scoring calculations are side-effect-free functions with unit tests and versioned assumptions.
  • Adapters wrap every external dependency. Trade data, email, SMS, WhatsApp, AI, payments and maps each sit behind an interface with a mock adapter. The real provider plugs in later without redesign.
  • Country-aware from day one. Currency, duty rules, regions and content are keyed by country_id. Nothing is hard-coded to Kenya.
  • History is kept, never overwritten. Research, trade and financial data are append-only revisions.

02Architecture & stack

The backend is a modular monolith: one deployable API with strictly separated domain modules. The only exception is Python analytics workers for ETL and statistics. This gives a small team fast delivery and simple transactions. Modules talk only through service interfaces and domain events, so any one can be split out later (Intelligence and Asset Cloud are the likely first candidates).

04Data model

Conventions

  • UUID v7 primary keys; created_at, updated_at, created_by, updated_by on every table; soft delete via archived_at.
  • Money stored as numeric(18,2) plus a currency code. Conversion uses dated fx_rates. Never floats.
  • Statuses are Postgres enums, and transitions are enforced in the service layer (see §5).
  • Every public record has publication_status (draft → in_review → approved → published → archived) and is_demo boolean. Demo rows are always labelled in the API response.

Evidence & versioning

Every important number links to evidence. opportunity_evidence records the claim, value, unit, source_id, source URL, data period, collection date, method and confidence (low/med/high). Trade and research values are stored as revisions rather than updates, with fields valid_from, superseded_by and ingestion_run_id. Financial models are versioned (financial_models.version). Each saved run freezes its assumptions and outputs, so a financing pack can always be reproduced exactly.

05Workflows & state machines

Each workflow is a state machine written as data: states, allowed transitions, the role required for each move, and guard checks. Every transition writes an audit entry and emits an event.

Hard-stop logic. HardStopService.evaluate(opportunity) runs nine rules: demand, market absorption, cost competitiveness, input route, technology, CAPEX, regulation, financing and quality. Each rule reads its thresholds from a table (hard_stop_rules), so analysts can tune them without a deploy. Any failure sets validation_status = NO_GO and records the reasons.

06Calculation engines

All engines live in one shared package, @firmplant/engines. They are pure TypeScript using decimal.js with no I/O, so the same code runs on the server and in the browser for live calculators. Every result carries the engine version and a hash of its inputs.

  • Financial engine. Inputs: CAPEX (10 lines), OPEX (9 lines), revenue (price × capacity × utilisation × product mix), financing (equity, debt, rate, tenure, grace). Outputs over a 10–15 year cash flow: gross profit, EBITDA, EBIT, tax, working capital, break-even, payback, IRR (Newton's method with a bisection fallback), NPV, DSCR per year and debt schedule. Returns Conservative, Base and Upside scenarios.
  • Landed-cost engine. Supplier price + freight + insurance + duties and taxes (from country tariff tables, by HS code) + port + clearance + inland + financing and handling. Result is compared with the local cost to give the import vs local verdict and the size of the advantage.
  • Scoring engine. The internal 100-point score across 11 weighted dimensions. Weights are stored and versioned. The score is never exposed through public endpoints (enforced by the API's response schema).
  • Financing calculator. Amortisation with a grace period, monthly and annual debt service, DSCR and cash after debt service. Shared with the public site.
  • Plant sizing / wizard recommender. Scales reference plant configurations by capacity (a CAPEX scaling exponent, stored per process) and matches wizard answers to published opportunities.

07API design

A versioned REST API at /api/v1 with an OpenAPI 3.1 spec generated from the code, and typed clients generated for the Next.js app. There are three surfaces: public (read-only, cached, published records only), portal (customers and suppliers, limited to their own records) and admin (internal roles). Conventions: cursor pagination, ?filter[field]= and ?sort=, errors in the standard RFC 7807 format, and idempotency keys on POST requests that create leads, RFQs or payments.

08Access control

Permissions take the form resource:action[:scope], e.g. opportunity:approve:financial or lead:read:assigned. Roles are bundles of permissions stored in the database. A request guard checks the permission; a policy layer then checks ownership (org, assignment, project membership). Financier and customer access is always row-scoped.

09Data ingestion

Pipeline: source → ingest → validate → normalise → map → store → analyse → signal → human review → publish. Each source is an adapter with fetch(period, scope), validate(raw) and normalise(raw) → TradeRecord[]. Raw data goes to a staging schema first. Only validated, mapped rows are promoted to core, each tagged with an ingestion_run record (source, URL, scope, period, method, confidence, row counts, errors).

  • Candidate sources, subject to licence review: international trade databases (UN Comtrade, ITC Trade Map), national statistics offices and revenue authorities, FAOSTAT for agricultural production, and published tariff schedules. Proprietary sources are entered manually by analysts with evidence attached.
  • MVP: CSV/XLSX import with column mapping, plus one automated trade-data adapter. Everything else uses mock adapters seeded with clearly labelled demo data.
  • Engines 1–5 run as scheduled jobs over core data and write signals rows (engine, HS code, country, metrics, rationale). Analysts promote signals to Discovered opportunities.

10AI orchestration

  • A provider-agnostic LlmProvider interface (complete, embed, tool-call), with per-task model routing and cost tracking in ai_runs.
  • Retrieval over approved data only. Embeddings (pgvector) index published opportunities, approved research and supplier records.
  • Every factual claim must cite its source. Tools return rows with IDs; answers must reference those IDs, and a validator rejects prices, trade values, certifications or financing statements that don't cite one.
  • AI drafts go into the content approval queue. They are never published automatically, and customer-facing assistants may not promise financing or returns.

11Security, audit & compliance

  • argon2id password hashing; one-time-code (TOTP) MFA, mandatory for internal roles; session rotation; lockout and rate limiting (Redis token bucket) on auth and public POST routes.
  • Every request body validated with zod/class-validator; CSRF protection on cookie sessions; strict CORS; security headers via Helmet.
  • Uploads: MIME type sniffing, virus scanning job, private bucket, signed links valid for 5 minutes, access checked per document.
  • Encryption at the column level for sensitive financing and ID data; secrets held in a managed vault; TLS everywhere.
  • Audit log: an append-only table (database role has INSERT only) with user, action, entity, before/after JSON diff, IP, user agent and request ID. Written automatically by a data-layer hook for audited models, and explicitly for workflow transitions.
  • Kenya Data Protection Act alignment: consent records, data export and deletion requests, and data-retention policies.

12Testing & quality

  • Engines: unit tests against reference spreadsheets (golden files) for IRR, NPV, DSCR, payback, landed cost and scoring. Target ≥ 95% coverage.
  • Workflows: transition tests for every state machine, including forbidden transitions and self-approval attempts.
  • Access control: a generated test matrix of role × endpoint × expected status.
  • Integration: the API tested against a real Postgres in a container (Testcontainers). Contract tests on the OpenAPI spec. End-to-end tests (Playwright) of the full customer journey, from KES 10M → enquiry → CRM lead.
  • SEO: snapshot tests of metadata, canonical URLs, sitemap and structured data.
